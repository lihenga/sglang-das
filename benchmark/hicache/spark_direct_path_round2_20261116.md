# 直通路径第二轮：实际改动、机制对照与物理卡定位

承接 [完整直通路径复核](spark_direct_path_audit_20261116.md)。本轮实际实现了 session 合并刷新和有写入语义的 offload 合批，并在同一八卡 1P1D 环境做相邻 A/B。没有继续修改 attention kernel，也没有重跑纯算。

## 实现过的两项候选

### Session 刷新合批

当前请求进入 admission-time refresh 时，最多合并 8 个已完成预取、未取消的私有 session，一次调用 native `batch_get_session_refresh`。后续请求仍检查自己的租约年龄；共享 session 保留强制刷新。每组单独解释结果，某组失败不使其他组误判成功；短响应/异常失败关闭；RPC 返回不更新已经结束、共享或换代的 Python lease base。

它减少的是调用次数，没有跳过 Master 的逐 key 元数据查询。原版在新增“多请求只调用一次”“组间失败隔离”“换代 lease base 不被旧回复覆盖”等测试失败，候选版通过。

### 有写入语义的 offload 合批

后台线程取出首个任务后，非阻塞收集队列中最多 8 个任务，分别等待各自 GPU event，再统一调用 `batch_set_v2`。每个原任务仍有独立结果、指标和 `task_done`，顺序不变，原节点锁仍由既有完成路径释放。缺少/短结果失败关闭；异常时给每个任务返回失败；保留停止 sentinel。

同时修正候选中的同 pool 多 transfer 结果拼接：原实现字典覆盖只保留最后一项，合批候选必须累积全部 page 结果才能回填原任务。没有用禁写回冒充优化，也没有增加定时延迟等待凑批。

单测在 `.29 / zhy-4B` 的独立 `feature/optimize_main` 源码中执行，首轮相关回归 **82 项、1,042 子场景通过**；之后补充了批大小上限、停止标记、side-pool 失败归属、共享 session 和同 pool 多 transfer 用例，补充回归也通过。测试只覆盖相应逻辑，不替代真实 native 并发压力验收。

## 正式 A/B：机制减少，整机收益未成立

固定此前 Spark / Mooncake wheel、SWA kernel、32K prefill 预算，P 卡0–3 / D 卡4–7。输入 64,000、1 输出、并发32、48 独立前缀，精确 PC95/90；每轮清 P/D L1。对照顺序为 control→lease→write→both，再反向复测；第二轮 PC 顺序也反转。每个配置和轮次使用独立新后缀。

初次 driver 误复用了不同配置的后缀 seed，校验捕获到一条 PC95 请求命中 61,568 而非 60,800 tokens；该组保留为无效诊断，不计性能。正式结果是修正后 `r2/r3` 的 16 组、768 请求。

| 配置 | PC95 两轮 input tokens/s | PC90 两轮 input tokens/s | 合并后对 control |
|---|---:|---:|---:|
| control | 151,769 / 149,780 | 90,085 / 90,630 | 基准 |
| 仅 session 合并刷新 | 150,020 / 150,826 | 90,213 / 90,485 | −0.23% / −0.01% |
| 仅 offload 合批 | 150,694 / 147,086 | 91,316 / 90,521 | −1.26% / +0.62% |
| 两者组合 | 151,823 / 152,387 | 90,564 / 91,069 | +0.89% / +0.51% |

合并按总 tokens / 总 elapsed 计算。各正式组均通过精确缓存命中、device/memory read 0、四 P rank DFS 读取与预取消费字节一致、读取/分配失败 0 的校验。

同一组 PC90、TP0 的 native 边界数据：

| 机制 | control | 对应候选 | 解释 |
|---|---:|---:|---|
| session refresh 次数 | 38 | 6（仅 lease） | 调用少了，但 key 总数 34,808→35,724，逐 key 处理仍在 |
| session refresh 累计 wall time | 1.215s | 1.161s | 没有按调用次数同比缩短 |
| native put 次数 | 103 | 27（仅 write） | 合批确实执行，未只是设置开关 |
| native put 累计 wall time | 3.566s | 2.741s | 后台时间下降，但与前台重叠，不能全算成可回收波次时间 |

**处理决定：这两个完整候选不进入 PR 生产代码。** 它们有机制上的效果，但当前数据不支持稳定端到端收益，增加会话/完成路径复杂度不划算。源代码补丁、测试及实测证据保存在实验目录，便于后续针对不同负载验证。此前 PR 已有的两处小范围 metadata 改动不受此决定影响。

## 更大的可复现差异：慢点跟随物理卡0

重新采集原映射下的 6-step PC95 trace，然后保持模型、kernel、预算、客户端负载不变，将 P 的 `HIP_VISIBLE_DEVICES` 从 `0,1,2,3` 改为 `1,0,2,3`，只交换逻辑 TP0/TP1 的物理卡。每份 trace 的 attention 调用数均为 216、grid 组成一致。

| P 映射 | 逻辑 rank | 物理卡 | attention 累计 | all-gather 累计 |
|---|---|---|---:|---:|
| 0,1,2,3 | TP0 | 0 | 11.247s | 1.286s |
| 0,1,2,3 | TP1 | 1 | 4.722s | 8.884s |
| 0,1,2,3 | TP2 / TP3 | 2 / 3 | 各约4.723s | 9.088s / 8.778s |
| 1,0,2,3 | TP0 | 1 | 4.723s | 9.193s |
| 1,0,2,3 | TP1 | 0 | 11.335s | 1.306s |
| 1,0,2,3 | TP2 / TP3 | 2 / 3 | 4.725s / 4.722s | 9.066s / 8.834s |

换位后的非 profile 吞吐 PC95 为 **151,500**、PC90 为 **90,527 input tokens/s**，仍接近对照。因为物理卡0仍在 P 的 TP 组内，单纯交换 rank 并没有消除慢设备/资源路径。

**已验证：长耗时跟随物理卡0，而非固定逻辑 TP0。** 原“TP0 特有框架开销”不能解释这个结果。其他 rank 的 all-gather 长等待与这个慢点相伴；这些累计时间不是端到端比例，不能相加，也不意味着 collective 全部是网络传输。

**尚未验证：物理卡0慢的根因。** 仍可能是设备/驱动、与该设备绑定的传输上下文、内存/带宽竞争或其他资源路径。不能仅凭换位称为硬件故障；此前逐卡独立 attention 微基准接近，也不能替代带全部服务负载的对照。

## 下一步实验被驱动状态阻塞

按上述结果，下一项实测设计是将卡0移到低计算量的 D 端：P=`1,2,3,4`，D=`0,5,6,7`，仍使用全部八卡、各 TP4。该实验**没有产出有效性能结果**：

1. P/D 并行启动时 Lightop 的 `get_CUs()` 从 `rocminfo` 没读到 CU 数量，写 `LIGHTOP_GPU_CUS=None` 抛 `TypeError`。
2. 清理/顺序重启过程中多个实验 Python 进程停在 `evict_process_queues_cpsch` 的 D 状态；普通终止/强制终止未能清除不可中断驱动等待。
3. 2026-11-16 18:54–18:56 的内核记录包含 `hycu` 的 `gpu_device_link_status_check` / `gpu_device_indirect_rreg` 等堆栈；SSH 出现间歇性响应延迟。尚不能将该次启动故障反推为此前吞吐下降的唯一根因。
4. 已将 P/D 启动脚本恢复为 `0,1,2,3` / `4,5,6,7`，移除诊断注入，归档完整证据。**P/D 当前未恢复健康**；没有重置设备或重启服务器。

驱动恢复后先验收原映射和完整预热，再做 P/D 物理分配对照；若收益成立，再分别切分 Mooncake store 写回、P→D 传输和 GPU 计算，识别卡0的绑定资源竞争。完整预取命中的 native 恢复快路径仍未实现，不把它写成已完成的优化。

## 当前结论

- 新的 session/写回候选已经实际实现并测过，当前不保留，原因是缺乏稳定吞吐收益。
- 当前更大的可复现线索是 P 的物理卡0执行时间约为同形状同调用数其他卡的 2.4 倍，其他 rank 等待；**不是已经证明 Mooncake 无瓶颈，也不是已经证明某个 kernel 算法有问题**。
- 主因仍需恢复环境后继续做资源隔离，不能宣称瓶颈已经解决。仍未达到 PC95 15×、PC90 9×。

原始证据：数据盘实验根目录下 `round2/`、`results/t2-*`、`logs/round2-*` 和 `round2-evidence.tar.gz`。本地整理目录 `direct-path-optimize-round2-20261116/` 保存候选 patch、8-rank trace 对照（两种映射各四 rank）、stage summary、测试和失败状态。所有 DFS/日志/临时数据继续位于 `/stortest/zhy_spcae/fixbug/spark-perf-tuning-20261116`，没有删除共享数据。
